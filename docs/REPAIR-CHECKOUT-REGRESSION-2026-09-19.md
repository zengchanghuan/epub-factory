## 已确认的问题与修复

| 问题 | 修复后的行为 |
| --- | --- |
| 生产 `ALIPAY_PUBLIC_KEY` 实际是可解析的私钥，SDK 无法验证支付宝响应；检查的 10 份部署备份也没有有效平台公钥 | 初始化严格加载 RSA 公私钥，拒绝私钥、证书、应用自身公钥和短密钥；配置错误时禁用支付，保留其他服务启动，并给出脱敏错误 |
| SDK 成功返回的是已验签的业务层 JSON，预下单仍按外层 envelope 取值 | 正确读取已验签结果；查单严格核对订单号，移除从验签异常文字提取交易状态的回退 |
| 独立修复漏回调后依赖浏览器补查 | 独立 API 后台线程确认付款，启动后也能继续；仅自动查询持久化 `checkout_started_at` 的订单，不凭历史订单号推定曾发起支付 |
| 诊断后刷新会恢复付款入口，后台也未验证是否存在可修复问题 | 诊断持久化并重新核验源文件；无需修复、损坏 ZIP、伪 EPUB 拒绝付款，可读书的局部资源警告不阻断可进行的格式修复 |
| 按钮替换文本丢失价格节点；网页支付替换容器后二维码节点失效；旧异步结果可能覆盖新任务 | 固定 DOM 节点，分开切换支付容器；跨任务响应隔离，已确认状态不被旧待付款结果覆盖 |
| 二维码 CDN 地址返回 HTTP 404 | 首页和修复页使用随站点发布的 `frontend/vendor/qrcode.js`，保留 MIT 许可证 |
| 修复页缺少报价展示和付款点击记录 | 实际展示和点击触发浏览器事件，付款成功只能由服务端验签回调或可信查询写入 |
| 新成交邮件临时入队失败后可能永久丢失 | 付款确认时同时持久化待通知标记；独立重试事件和邮件入队，重复事件不重复发信，不补发历史订单通知 |

本轮仍无法由站内 `pending_payment` 断定历史订单没有真实付款。特别是 5.99 元历史记录包含转换和翻译等服务，不能把全部未确认成交归因于独立修复页故障。后续只读验签检查的单笔旧修复交易返回 `ACQ.TRADE_NOT_EXIST`；这不能推广为其他历史订单均未付款。

## 边界

- 新独立修复默认 0.99 元；历史冻结报价和测试单标记保留。
- 后台每 5 秒最多查询一笔，单订单采用 15 秒至 1 小时退避；超过 48 小时标记待人工核对，不把订单改为失败。
- 浏览器补查最快 45 秒一次，每次打开任务最多 10 次；查询不可用明确提示“请勿重复支付”。已发起付款的历史订单即使源文件现在不可修复，也保留核实付款入口。
- 回调和查询按精确订单号、冻结金额确认，同一 API 进程串行处理并避免重复修复。当前部署应继续保持单 API 进程；这里没有新增跨进程分布式锁。
- 新确认的付款事件和商户邮件入队最多补偿 8 次，30 秒起退避、最高 5 分钟；仍失败保留 `confirmation_delivery=attention_required`。邮件实际投递继续使用原有 outbox 派发机制，入队不等于送达。
- 配置无效时不自动请求支付宝，也不消耗查单重试次数；已验证付款的本地修复与通知补偿仍可恢复。

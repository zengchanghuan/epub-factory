## 复盘依据与优先级

本次会话的生产只读复盘核验到最近 30 天 5 笔真实支付。其中 4 笔失败；1 笔成功且存在成品与下载响应。两笔同额订单的输入摘要相同；一笔翻译有 31 次尝试。此处记录观察结果，不能把 HTTP 下载响应当作读者验收，也不能把失败订单自动视为已退款。

先保障已付款任务可以恢复、失败有明确出口、交付证据可追溯，再增加流量。

## 已实施

| 环节 | 修复 | 故障时的行为 |
| --- | --- | --- |
| 支付到任务派发 | `job_dispatches` 持久化派发意图与付款放行、批次放行、重试在同一事务提交 | 队列不可用时保留 pending，后台每 5 秒扫描、指数退避重发；浏览器关闭不影响恢复 |
| 重复消息 | 每次尝试有独立 attempt ID；已有执行租约负责单次执行；所有成品使用独立路径 | 消息允许重复投递，已完成或过期尝试不执行；派发记录直到任务终态才清除 |
| 进程中断 | running 超过 10 分钟无状态更新时检查执行租约 | 活跃执行器仍持锁则保持运行；确认无执行器后标为 EXECUTION_INTERRUPTED，保留缓存，等待人工/用户处理，不自动反复消耗模型费用 |
| 状态写入 | SQLite/PostgreSQL 写入前对任务行加写锁，尝试校验与状态、chunk、chapter 写入同一事务完成 | 旧执行器不能越过重试/取消的事务覆盖新任务；批次创建全部成功或全部回滚 |
| 支付补偿 | 对账默认每 5 分钟调度，默认检查滞留超过 5 分钟的订单；WAIT_BUYER_PAY 不做本地超时取消 | 支付网关仍开放付款时保留订单；迟到的有效支付仍可放行。只有网关 TRADE_CLOSED 才关单 |
| 失败重试 | 自助重试默认最多 3 次，配置范围 0–10，旧值 -1 按 3 处理；保留每次终态、错误、QA 和成本历史 | 结构校验失败、校验服务不可用、连续两次同类失败转人工；管理员核验付款、确认额外成本后仍可重试 |
| 重试资格 | 客户重启前查询并核对原订单身份、成功状态及冻结金额 | 取消未付款任务不能获得付费执行权；查单不可用时提示等待/联系客服，不要求另付一单 |
| 重复上传 | v2 单本与批次按用户/浏览器会话、内容摘要和规范化设置去重，并用可续期锁串行建单 | 7 天内、最近 1000 条同主体任务中的相同提交返回原任务，前端打开原订单；已付款后取消也保留去重保护 |
| 验收 | ConversionResult 默认未验收；任何错误码、部分翻译失败、缺少成品均不标成功 | 失败结果不开放下载，原有 PDF 人工复核与正文/导航交付检查仍生效 |
| 成品完整性 | 成功后存 SHA-256、字节数、attempt ID、验收时间；单本、批次和管理员结果下载核对摘要 | 缺失/篡改返回 410；批量 ZIP 每次请求独立生成，响应结束清理，避免并发覆盖 |
| 排障证据 | 保存 EPUBCheck 错误码、资源路径、行列；最多 100 条，不保留原始命令输出/书籍片段 | 管理员订单详情展示派发次数/失败、格式校验、成品凭据与尝试历史；客户看到人工处理及无需重复付款的提示 |

去重依赖稳定用户或浏览器会话。不按共享 IP 推断同一人；匿名用户更换浏览器、缺少会话、改变设置、旧任务无摘要或超过上述范围时，不能保证跨订单去重。旧已成功成品没有摘要时兼容原下载行为，不伪造历史验收证据。

## 上线与存量订单处理

1. 发布前核对当前运行任务，等待执行器空闲，避免部署重启中断正在翻译的客户订单；备份数据库及配置。现有未提交 PDF 工作需要单独核对发布范围。
2. 保持 API 与 Celery Worker 使用同一持久化数据库与 Redis 配置。启动 API 时 `Base.metadata.create_all` 新增派发表；已有表和订单金额不改写。内存 store 不具备重启恢复保证。
3. 启动/重启 API、Worker 与 Beat 后检查 5 分钟对账调度已生效。对账需要 Beat 和可用 Worker；单并发 Worker 忙于整书翻译时可能延后，不是严格 5 分钟到账 SLA。旧 `RECONCILE_CRON_HOUR/MINUTE` 不再控制该任务。
4. 派发器自动接管旧 pending，不重开失败、取消或待付款任务。旧 running 且没有派发表记录的任务须人工核查，不能直接假定进程已丢失。存在旧积压 pending 时，接管会执行此前已经接受的工作，应在发布前核查。
5. 使用测试订单验证：有效支付 → 数据库意图 → 队列 → 单次执行 → 验收摘要 → 下载；断开队列后恢复，重复回调不得产生第二次执行。邮件订阅、真实 Redis/Celery 崩溃恢复、外部支付与 PostgreSQL 运行环境仍需上线验证。
6. 对历史 4 笔已付失败订单逐笔核对：先查两笔同源转换的 EPUBCheck 资源缺失，再审查翻译原件与缓存；修复后经管理员确认成本才重试。若不能交付，再决定退款/沟通方式。生产订单未回写，未退款或发客户消息；隔离重跑结果见下方补充。

回滚代码前先停派发扫描并确认执行器状态。派发表可以保留，旧程序不会读取；单纯回退代码会失去本次恢复与重试保护。
